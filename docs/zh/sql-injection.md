# AI 项目安全基线：SQL 注入防护与测试指南

> 检查项编号：SQ-01 至 SQ-10（上线门禁）、SQ-R1 至 SQ-R7（代码审查）
>
> 适用范围：AI 辅助开发的新项目（Web 应用、API 服务、全栈产品）。
> 目标：把 SQL 注入防护做在**设计阶段**，把注入测试做在**上线之前**，而不是被攻击之后。
> 本文档是通用基线，与具体项目、语言、数据库无关；示例以 JavaScript/TypeScript + SQLite/D1 为例，原则可平移到任何技术栈。

---

## 0. 核心原则（先记住这五条）

1. **默认参数化**：用户输入永远通过占位符（`?` / `$1` / bind 参数）进入 SQL，任何拼接都是例外，例外必须显式标记且被审计。
2. **原始 SQL 通道用类型系统标识，绝不用字符串标记**（见 §2.2，最容易被忽视的坑）。
3. **格式白名单优先于转义**：能校验格式的（日期、邮箱、枚举值）先校验；必须自由文本的才转义。
4. **错误信息不外泄**：SQL 片段、表结构、数据库报文只进服务端日志，对客户端一律返回通用文案。
5. **上线前必须做一轮注入测试**（静态审计 + 黑盒探针），并把测试用例沉淀进回归。

---

## 1. 为什么 AI 生成的代码要特别小心

AI 生成的数据库访问层常见三类隐患，review 时重点盯：

| 反面模式 | 危险点 |
|---|---|
| 模板字符串直接拼 SQL | `` `select * from t where email = '${email}'` `` —— 经典注入 |
| **字符串标记实现“原始 SQL”通道** | 用 `__RAW__` 之类的魔法字符串区分“原样拼接”，但执行层对**所有**插值做前缀/后缀检查 → 用户输入首尾伪造标记即可注入（见 §2.2） |
| 错误处理直接透传 | `catch (e) { return error(String(e)) }` —— 把 SQL 模板和库报文泄漏给攻击者，帮对方摸清表结构 |

## 2. 设计阶段：架构层防注入

### 2.1 数据访问层：只有一条入口

- 所有 SQL 经由**唯一的**数据访问函数/封装执行，禁止业务代码直接拿 driver 连接对象写查询。
- 该封装默认对每个插值做参数绑定；不提供任何“绕过”口子。

```ts
// 唯一入口示例（tagged template / 查询构建器均可）
const rows = await sql`select id from users where email = ${email} limit 1`;
//        ↑ email 自动变为 ? 占位符 + bind，插入多少恶意内容都只是字符串字面量
```

### 2.2 原始 SQL 通道：用类实例，不用字符串标记（高发陷阱）

偶尔确实需要拼接 SQL 片段（动态 where、列名白名单展开）。此时“标记这是原始 SQL”的实现方式决定安全性：

```ts
// ❌ 反面：字符串标记 —— 用户输入可伪造
const RAW = '__RAW_SQL__';
const unsafe = (t: string) => RAW + t + RAW;
// 执行层对所有插值检查：val.startsWith(RAW) && val.endsWith(RAW) → 原样拼接
// 攻击者提交 "__RAW_SQL__' or 1=1--__RAW_SQL__" 即可命中检查，注入成立。

// ✅ 正确：类实例标记 —— JSON/表单永远无法伪造
class RawSqlFragment { constructor(public text: string) {} }
const unsafe = (t: string) => new RawSqlFragment(t);
// 执行层：if (val instanceof RawSqlFragment) splice(val.text) else bind(val)
```

判定标准：**攻击者能控制的只有“字符串值”；凡是“值本身决定走不走原始通道”的设计都是洞。** Python/Java/Go 同理——用专用类型/结构体，不用魔法字符串、不用约定的前缀后缀。

### 2.3 动态标识符（表名/列名/排序字段）：白名单映射，不做转义

标识符不能参数化，所以只能白名单：

```ts
const SORTABLE = { created: 'created_at', price: 'price' } as const;
const col = SORTABLE[req.query.sort] ?? 'created_at';   // 查不到就用默认值
```

禁止把用户输入直接拼进 `order by` / 表名 / 列名——转义引号对标识符注入无效。

### 2.4 特殊场景速查

| 场景 | 做法 |
|---|---|
| `LIKE` 模糊搜索 | 参数化传值；用户输入中的 `%` `_` 需转义（`\%` `\_`），防通配符拖库 |
| `IN (...)` 列表 | 数组整体作为参数由封装展开为 N 个 `?`，不要 join 成字符串 |
| 日期/时间范围 | 先正则校验格式（如 `^\d{4}-\d{2}-\d{2}`）再使用；**校验函数的 fallback 不能原样透传非法输入**——宁可返回 null/报错 |
| 枚举型参数（status/type） | `if (!['a','b'].includes(v)) reject` 白名单后直接拼也安全 |
| 必须拼接的自由文本 | 走集中式转义函数（见 §2.5） |

### 2.5 转义函数：全局只有一个

- SQLite/MySQL 单引号翻倍（`'` → `''`）是正确的字面量转义；SQLite **没有**反斜杠转义。
- 全项目只定义一个 `q(s)` 之类的转义函数，review 时 grep 它的使用点；散落各处的 `.replace(/'/g, "''")` 是漏网之鱼的来源。
- 记住：转义是兜底，参数化才是常态。每个 `q()` 调用点都应该问一句“为什么不能参数化”。

### 2.6 影响面控制（纵深防御）

- 数据库账号最小权限：前台业务用读写账号，报表/分析用只读账号。
- 禁用多语句执行（driver 默认多数已禁，确认一下）。
- 后台/admin 接口与前台接口分开鉴权层级；admin 里的查询同样要参数化——**“反正有登录墙”不是不写安全的理由**，admin session 被盗或门禁误配时注入就是最后一道防线。
- 免登录接口（埋点、表单、回调）列入最高优先级审计对象：它们是攻击者唯一无门槛可达的注入面。

## 3. 编码阶段检查清单（Code Review 用）

- [ ] **SQ-R1** 全项目搜 `\$\{` 出现在 SQL 字符串里的每一处：是参数占位还是拼接？
- [ ] **SQ-R2** 搜 `+ email`、`+ id` 等字符串相加进 SQL 的写法（老代码常见）
- [ ] **SQ-R3** 原始 SQL 通道的实现是“类型/类实例”还是“字符串标记”？字符串标记一律返工
- [ ] **SQ-R4** 用户输入 → SQL 之间有没有“不改大小写、不校验格式”的裸路径？（trim/lowercase 恰好破坏 payload 的属于侥幸，不算防御）
- [ ] **SQ-R5** catch 块是否把 `error.message` 原文返回给客户端？DB 类错误应替换为通用文案
- [ ] **SQ-R6** 日期/枚举校验函数的 fallback 分支是否会透传非法输入？
- [ ] **SQ-R7** 排序、筛选、分页参数是否走了白名单或强类型转换（`Number()` 后再拼）？

## 4. 测试方法论：上线前的注入测试

### 4.1 静态审计（10 分钟，先做）

对数据访问封装和全部业务查询文件跑以下检索，逐条人工确认：

```text
\$\{             → SQL 模板字符串里的插值
\.prepare\(      → 是否有绕过封装的直接调用
unsafe\(|raw\(|RAW → 原始 SQL 通道的全部使用点
where \+=|whereStr \+= → 动态 where 拼接
ilike|like '%   → LIKE 拼接点
String\(err(or)?\) → 错误信息是否回流到响应
```

### 4.2 黑盒探针

对部署好的站点发请求，每项一次，判定靠状态码/响应差异。**只对自己有授权的项目执行。**

**第一批：经典 payload（验证参数化）** —— 期望与正常输入响应一致：

```text
x'||(select 1)--@example.com
' or '1'='1
1; drop table x--
%"@example.com"@example.com
```

判定：登录/表单类接口应返回与“正常错误输入”相同的响应（如 401/400）。若出现 500、明显变快变慢、或响应内容不同 → 有拼接，立即停。

**第二批：框架专属探针（验证原始通道标识）** —— 针对项目自己的“原始 SQL”机制构造伪造输入：

- 若用字符串标记：把标记拼在输入首尾再夹一个引号，如 `__标记__'__标记__`
- 判定：**200 + 正常业务响应 = 安全**（值被当字面量存储）；**500 且报错含 SQL 片段 = 注入洞确认**

**第三批：免登录接口优先** —— 埋点、回调、公开搜索、表单。这些接口无需账号即可触达，任何发现都直接定高危。

### 4.3 测试红线（不要把探测变成攻击）

- ❌ 不要在生产跑高消耗 payload（如递归 CTE 生成百万行 `with recursive c(x) as (select 1 union all select x+1 from c where x<5000000)`）——那是攻击者用来烧 CPU 的 DoS 手法，自己测试也足以拖垮服务。
- ❌ 不要在别人未授权的站点做任何注入测试。
- ✅ 探针选**单次请求、无副作用**的：读接口优先；写接口只发能靠“成功/报错”判定的最小 payload。
- ✅ 每个探针先发一个正常基线请求做对照，判定看**差异**而不是绝对值。

### 4.4 结果判定速查

| 观察 | 结论 |
|---|---|
| 响应与基线一致（401/400/200 正常文案） | 参数化生效，通过 |
| 500 且报错含 SQL 片段/表名 | 拼接洞确认 + 错误泄漏双重问题 |
| 响应明显变慢（时间盲注） | 可能有可执行表达式注入 |
| 同 payload 多次请求结果不稳定 | 排查缓存/重试逻辑后再判 |

### 4.5 回归与持续防护

- 把本次发现的 payload 写成自动化用例（每个入口 × 每类探针），进 CI 或部署后 smoke test。
- 监控侧兜底：数据库扫描行数/请求量异常告警（注入常伴随全表扫描）、5xx 突增告警、错误日志里的 SQL 报错聚类。
- 依赖升级后重跑静态审计：数据访问封装本身也是代码，会被改坏。

## 附：一句话记忆

> **“用户输入决定走不走原始 SQL 通道”是所有注入洞的共同形状。**
> 参数化挡住 99% 的注入；剩下 1% 的洞几乎都藏在“框架自己的原始 SQL 机制”和“后台/免登录接口的裸拼接”里——测试时优先打这两处。
