## 这个仓库解决什么问题

AI 编码工具能把功能做得很快，但它默认不会替你考虑这些：

- 上线后有人扫 `/.env`、扫后台接口、伪造 OAuth 凭证怎么办；
- 一条 AI 写的 SQL 是参数化的还是字符串拼接的；
- 一个后台列表页每次加载扫几百万行，账单悄悄涨；
- 面向海外用户时，年龄验证、退订、自动续订、DMCA 有没有硬伤；
- Serverless 用量被刷或查询写崩了，怎么第一时间发现；
- 接手的二手域名以前挂过博彩、钓鱼或垃圾站，信誉黑档案拖累 SEO 和广告审核。

这些问题的共同点是：**开发阶段看不出来，上线后才以事故或账单的形式出现。** 本仓库把它们整理成带编号、可执行、可留证的检查项，并给出可以直接交给 AI 助手执行的提示词。

## 适合谁用

- 用 AI 做 side project、SaaS、出海网站、订阅制产品的独立开发者；
- 没有专职安全 / 合规 / DBA 的小团队；
- 接手上线前 review、或需要给项目做周期性体检的人；
- 想给团队的 AI 编码流程加一道「上线门禁」的工程负责人。

## 怎么用

### 方式一：把提示词交给 AI（推荐）

复制下面整段（GitHub 代码块右上角有复制按钮），粘贴给 Cursor、Claude Code、Trae 等任意能读代码的 AI 助手，让它按清单逐项体检你当前的项目。

```text
你是我的「AI 项目体检员」。请按 ai-project-checkup 仓库里的清单，对我当前打开的项目做一次上线前体检。

仓库地址：https://github.com/foodpm/ai-project-checkup

工作步骤：
1. 先读取仓库根目录 README，以及 docs/zh/ 下六篇文档：
   attack-surface.md、sql-injection.md、backend-performance.md、
   overseas-compliance.md、cloudflare-usage.md、domain-history.md。
2. 先给项目画像：技术栈、是否有前端/后端/数据库/支付/邮件/用户上传/
   第三方脚本，判断哪些文档适用、哪些不适用。
3. 逐条检查有编号的项（AS-01…AS-21、SQ-01…SQ-10、BP-01…BP-13、
   CO-01…CO-06、CF-01…CF-03、DH-01…DH-03）。每条只给一个结论：
   通过 / 不通过 / 待核验 / 不适用。
4. 结论必须有证据：能指到 文件:行号、配置项或命令输出；
   确认不了的写「待核验」，不要猜。
5. 先不要改代码。输出一份体检报告，按优先级排序：
   P0（未完成不得上线）、P1（上线后 30 天内）、P2（持续治理）。
   每个不通过项给出最小修复方案和验证方法。
6. 报告最后附一份「10 分钟手检清单」，只保留本项目确实需要人工确认的项。

如果无法访问网络，请直接告诉我，我会把六篇文档粘贴给你。
```

拿到报告后，建议先处理 P0，再让 AI 按「最小修复方案」逐项改，每改一项跑一次验证。

### 方式二：精简版提示词

时间有限、或只想知道「现在能不能上线」时用这段：

```text
请以 https://github.com/foodpm/ai-project-checkup 的清单为准，
对我当前项目做一次最小上线体检。只检查三类：
1. 攻击面文档的「上线前 10 分钟快速清单」全部条目；
2. SQL 文档的 SQ-01 至 SQ-10；
3. 性能文档里与本次改动直接相关的 BP 条目。
每条给：通过 / 不通过 / 待核验 / 不适用 + 证据（文件:行号）+ 最小修复。
不要改代码，只出报告。
```

### 方式三：手动手检

适合不放心把代码交给 AI、或需要留审计证据的场景。

1. 打开对应文档，从「上线前 Checklist」或「快速清单」开始，不必通读全文；
2. 每检查一项，在结果表里记下编号、结论、证据（文件:行号 / 命令输出 / 截图）；
3. 不通过的项按文档中的「防护 / 条款」改，改完用「验收测试」复验；
4. 每季度或大改版后全量过一遍；合规类按文档里的 P2 周期复查。

## 体检结果怎么记录

建议每个项目维护一张这样的表（可以直接让 AI 生成 Markdown）：

| 编号 | 结论 | 证据 | 修复方案 | 负责人 | 复审日期 |
|---|---|---|---|---|---|
| AS-01 | 通过 | 6 个路径均 404，见截图 | — | — | 2027-02-08 |
| SQ-02 | 不通过 | `src/db.ts:120` 用字符串标记 | 改为类实例标识 | @dev | 2026-11-15 |
| CO-05 | 待核验 | 首屏截图待补 | — | @pm | 2026-11-20 |

结论只用四种：通过 / 不通过 / 待核验 / 不适用（不适用必须写理由）。「隐私政策里写了」「供应商后台有开关」不算通过。

## 六项检查怎么配合

| 阶段 | 用哪些文档 | 目的 |
|---|---|---|
| 接手二手域名 | 域名历史 | 查清域名前世，避免接手信誉黑档案 |
| 动手写之前 | 后端性能、SQL 注入 | 把索引、参数化、快照做进设计，避免返工 |
| 功能完成、上线前 | 攻击面、SQL 注入、海外合规 | 过安全与合规门禁，P0 清零 |
| 上线后第一周 | 边缘平台用量、性能 | 确认没有异常用量、慢查询、账单刺客 |
| 每季度 | 全部六篇 | 全量复审，更新证据与结论 |
